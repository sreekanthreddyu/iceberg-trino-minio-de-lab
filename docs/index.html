Core concepts

MinIO

MinIO supplies an S3-compatible object API. Buckets and objects store bytes; they do not provide Iceberg table semantics.

Apache Iceberg

Iceberg is a table format built from metadata JSON, manifest lists, manifests, data/delete files and snapshots. It enables atomic table commits, evolution and time travel.

REST Catalog

The catalog resolves logical table names to Iceberg metadata and coordinates catalog operations. It is separate from both compute and object storage.

Trino

Trino is the SQL compute engine. The Iceberg connector uses catalog metadata to plan queries and reads/writes table objects in MinIO.

PostgreSQL + Python

PostgreSQL acts as a mutable OLTP source. Python is the learning surface for ingestion control, validation, audit state and automation.

Watermarks + idempotency

Fixed source bounds define a run. Destination commit and watermark update must be designed so crashes cannot silently skip or duplicate business data.

Maintenance

Small files, snapshots and metadata accumulate. Compaction, snapshot expiration and orphan cleanup are operational procedures with retention and correctness consequences.

Step-by-step process

Step 1: Docker state

Learn image/container, network, port, health check, bind mount and named volume. Build PostgreSQL + MinIO first.

Break/recover: Remove containers with and without volumes; explain exactly what survives.

Step 2: MinIO

Create the warehouse bucket; learn endpoints, object keys, credentials and persistence.

Break/recover: Use wrong credentials and a wrong endpoint; distinguish authentication from connectivity.

Step 3: Trino

Add Trino and connect it to PostgreSQL before adding Iceberg. Learn catalogs, connectors and pushdown.

Break/recover: Break a catalog property and diagnose Trino startup/query logs.

Step 4: Iceberg REST catalog

Connect Trino → catalog → MinIO and verify each network path.

Break/recover: Stop the catalog, then MinIO; compare the two failure signatures and changed state.

Step 5: First Iceberg table

Create and insert through Trino. Inspect metadata JSON, manifests and Parquet objects in MinIO.

Break/recover: Explain why placing Parquet files in a bucket does not create an Iceberg table.

Step 6: Snapshots + time travel

Perform insert/update/delete operations and query Iceberg metadata/history.

Break/recover: Make a logically bad change, identify its snapshot and investigate via time travel.

Step 7: Schema + partition evolution

Add/rename columns and evolve partition strategy while understanding hidden partitioning.

Break/recover: Attempt an incompatible change; reason about metadata and data impact before recovery.

Step 8: Incremental ingestion

Implement fixed lower/upper watermarks, audit state and load control in Python yourself.

Break/recover: Crash after Iceberg commit but before watermark update; prove retry behavior.

Step 9: MERGE + deduplication

Define business key and deterministic deduplication, then upsert changed source rows.

Break/recover: Feed conflicting duplicates and inspect which rule wins.

Step 10: Quality + quarantine

Separate bad business records from infrastructure failures and retain replay context.

Break/recover: Inject invalid values and prove good records are preserved.

Step 11: Iceberg maintenance

Generate small files, measure them, compact, inspect snapshots and storage growth.

Break/recover: Predict candidates before snapshot expiration/orphan cleanup; treat cleanup as destructive.

Step 12: Observability + security + CI

Correlate run ID, source bounds, counts, snapshot and errors; remove hard-coded secrets; validate PRs.

Break/recover: Break one dependency and diagnose using only collected evidence.

Step 13: Capstone

Load a source delta to Iceberg, query it, inspect metadata and audit state, and explain the full system.

Break/recover: Predict a failure, inject it, recover without resetting the lab, and explain prevention.

Learning lab vs production

The first design is intentionally single-machine. Production needs durable object storage, catalog HA, distributed Trino topology, authentication/authorization, TLS, secret management, backup/DR, centralized metrics/logs, resource isolation, compatibility-tested upgrades, retention policy and rehearsed maintenance/recovery.

Daily completion test

Before moving on, explain: What problem does this component solve? What state changes? What happens if it fails halfway? Is retry safe? How is it secured and monitored? What changes at production scale?
